# GhostKey 收尾路径修复方案（2.0.37）

> 依据：一加 Ace 5（PKG110，内核 6.1.157-android14-11-o-g7cdd565ce1ed）
> 2026-11-12 夜间四轮 2.0.36 真机日志（21:48 / 22:38 / 23:15 / 23:54）逐行核对，
> 以及对 `main@851f63a` 基线与 2.0.36 补丁系列（C1~C7）的源码级确认。
> 配套交付：补丁 0008~0011（见 `ghostkey-patches/`），
> 双语设计说明已入库（0011，`docs/analysis/ghostkey-verify-gate-fixes-2.0.37*.md`）。

## 1. 背景与验证结论

2.0.36 补丁系列（C1~C7，详见《GhostKey失败路径修复方案_2.0.36.md》）的目的是修复
cred 捕获的结构性死代码（RC-1）与失败路径驻留问题。本轮四份真机日志给出了确定性答案：

| # | 时间 | 构建（可辨识特征） | 结果 | 关键过程 |
| --- | --- | --- | --- | --- |
| 35.log | 09:25 | 2.0.34 旧版 | 失败 | `cred=0 candidates=0` → `holding zombie`（原始 RC-1 现场，供对照） |
| 36.log | 21:48 | **A0** = C1~C7 原样（`clear attempt /12`，基线验证逻辑） | 内核级已成功，被验证门禁误判丢弃 → zombie | `candidate=1` 捕获成功；自第 10 次尝试的 proc 转储起显示 `Uid: 0 0 0 0`；`is dead errno=1` 全轮共 8 次 → 12 次耗尽 |
| 38.log | 22:38 | **A1** = A0 + 手工 EPERM 分支（cap 仍 12） | run1 手动中断；run2 euid 十二次未落 → zombie | `refuses our signals (EPERM)` 行生效（出现 3 次）；12 次尝试中 7 次走到验证、5 次因补发失败提前重试，euid/egid 始终未写入 |
| 39.log | 23:15 | **B** = 上限 24 + 自带 diag 段 | **成功** | 第 2 次尝试落地 → rootd → `su -c id` = uid=0(root)；suid/fsuid 交接时仍为 2000 |
| 40.log | 23:54 | **B**（同 39） | **成功（复现）** | 第 5 次尝试落地（含 2 次 page_miss）→ 八字段全零交接 → root ✓ |

构建辨识依据：36/38 打印 `clear attempt 1/12`，39/40 打印 `1/24`；`refuses our
signals (EPERM): its cred is root now` 与 diag 段（uname/ELF/--version/sig_enforce/
dmesg/ko found）在基线 `main@851f63a` 与 C1~C7 全部补丁中均不存在——为使用者在
自有构建中加入的改动。

**验证判定：**

1. **C1/C2 钉死验证**：四轮 2.0.36 日志全部出现
   `[cred-leak] candidate=1 ptr=... req=176 alloc=192`（旧版恒 `candidates=0`）。
   alloc=192 落在 C2 过滤窗口 `[176, ALIGN64(176)+8=200]` 内，call_site 命中。
   RC-1 根因修复在任何机型上成立的结论获得真机确认。
2. **C3 未被触发**：四轮全部捕获成功，「无 cred 快速退场」路径没有登场机会——
   这本身就是修复目标达成的体现；36/38 卡住时走的是 `g_cred_kva≠0` 的保守驻留
   分支，与 C3 注释声明的行为一致。
3. **GK-FAILFAST-01 之 ④ 达成**：Ace 5 从 0% 成功（2.0.34）变为 2/2 连续成功
   （B 构建），inject 阶段 36~55s 完成提权。
4. **新问题**：36/38/39 暴露了验证收尾环节的四个 C1~C7 范围之外的缺陷（W1~W3、K1），
   本方案以 C8~C10 修复，见第 3、4 章。

## 2. 现场证据

### 2.1 W1：36.log「赢在内核、输在门禁」全过程

36.log 第 823~831 行（第 10 次尝试的验证段）：

```text
[21:51:43] [cred] proc Uid:	0	0	0	0          ← 内核层面：cred 八字段已全部清零
[21:51:43] [cred] fields cleared, verifying
[21:51:43] [cred] child 14529 is dead errno=1          ← kill(pid,0) 得 EPERM，被判「死亡」
[21:51:43] [cred] proc State:	S (sleeping)           ← 紧接着却读到了 /proc 状态：进程活着
[21:51:43] [cred] proc Uid:	0	0	0	0
[21:51:43] [cred] proc CapEff:	0000000000000000
[21:51:43] [cred] child did not answer                 ← 管道答案从未被尝试
```

同一幕在第 10~12 次尝试连续重复（21:51:43 / 21:51:58 / 21:52:12）；追溯全轮，`is dead errno=1` 共出现 8 次，每一次都紧跟着 `State: S` 的活体 proc 转储。最终：

```text
[21:52:12] [uaf] missed page; holding zombie
```

**矛盾点是自证的**：`errno=1` 即 EPERM，而 EPERM 只在目标进程存在但调用者无权
发信号时出现——如果子进程真死了，errno 应是 ESRCH(3)。代码紧接着还成功读出了
它的 `/proc/status`（State: S），两行日志互相拆台。

### 2.2 W2：38.log euid 十二次未落

38.log 第 2 次运行（22:39:07 起）的清除进度：

```text
156:[22:39:37] [cred] clear attempt 1/12 cred=0xffffff88ad2b7540
289:[22:40:12] [cred] still uid=0 euid=2000            ← uid/gid 已清，euid 卡住
367:[22:40:27] [cred] still uid=0 euid=2000
562:[22:41:26] [cred] still uid=0 euid=2000
662:[22:41:48] [cred] still uid=0 euid=2000
743:[22:42:03] [cred] still uid=0 euid=2000            ← 此时已是第 10 次
820:[22:42:22] [cred] still uid=0 euid=2000            ← 第 12 次（最后一次）
```

期间 `/proc` 一直显示 `Uid: 0 2000 0 0`（uid、suid、fsuid 均已清零，唯独 euid 不落）。12 次尝试中有 7 次走到验证（`still uid=0 euid=2000` ×7），另 5 次因补发失败提前重试；而循环每个尝试都把四组字段**全部**补发一遍 UAF 周期——已清零的三组白吃了十几次 3.5~8 秒的周期，上限 12 被这些无效重发耗尽。对比同机另两轮：A0 第 ~10 次落地、
B 第 2 次落地，说明 euid 落地是当次 boot 页布局的运气问题，12 次上限不够冗余。

### 2.3 W3：39.log vs 40.log 的 rootd socket 对照

39.log 第 2 次尝试刚把 uid/euid 清零就通过了验证并交接（管道答案只含
uid/euid/gid/egid 四个值）：

```text
260:[23:16:38] [cred] proc Uid:	0	0	2000	2000   ← suid/fsuid 仍是 2000
262:[23:16:38] [cred] fields cleared, verifying
264:[23:16:38] [cred] answer uid=0 euid=0 gid=0 egid=0 ← 门禁只看这四个值 → rooted
```

rootd 随即在半清 cred 的 `prepare_creds()` 副本上出生：

```text
23:16:38 [rootd] sock uid=2000 gid=2000 mode=0666      ← 39.log：socket 属主 2000
23:56:01 [rootd] sock uid=0 gid=0 mode=0666            ← 40.log：全清轮 socket 属主 0
```

socket 属主取自 `current_fsuid()`，直接暴露了 rootd cred 副本里的 fsuid 差异。
此外 cred 子进程自身的 fork 判据只有 `uid==0 && euid==0`（`uaf_plant.c` 原
1840 行），即使父进程门禁收紧，子进程仍会在第一次探到 uid/euid 归零时就提前
fork rootd——两侧都要改。

### 2.4 K1：KSU 接管的三层障碍

40.log 的 `ksu_takeover.log` 完整记录了失败链：

```text
[ksu] begin uid=0 enf=Permissive
[ksu] setenforce_rc=0 enf=Permissive
[ksu] live_initial=no
[ksu] try: late-load --kmi android14-6.1
[ksu] rc=0                                    ← ksud 自注：rc 不是判据，静默失败也返回 0
[ksu] live=no
[ksu] try: late-load (no args, ksud picks the embedded KMI)
[ksu] rc=0
[ksu] live=no
[ksu] sig_enforce=cat: /sys/module/module/parameters/sig_enforce: No such file or directory
[ksu] ko found: none
[ksu] dmesg tail: ...（仅末半秒，261.157s~261.605s，未覆盖 late-load 时段）
```

结合四轮日志中反复出现的 `[cred] proc CapEff: 0000000000000000`，三层障碍按
确定性排序：

1. **CAP_SYS_MODULE 缺失（确定）**。写零循环只清 cred 的 uid/gid 组字段
   （+4/+12/+20/+28），不触碰 cap_* 位图；`init_module/finit_module` 在内核里
   硬性检查 `capable(CAP_SYS_MODULE)`，该检查读 `cap_effective`，**SELinux
   Permissive 不豁免**（capable() 的 capability LSM 分支不看 avc 的 permissive
   标志）。CapEff=0 → insmod 必得 EPERM → ksud 静默 rc=0。
2. **模块签名强制（高度可疑，未定罪）**。`/sys/module/module/parameters/
   sig_enforce` 节点缺失：GKI 配置在 `CONFIG_MODULE_SIG=y && !FORCE` 时才存在
   该节点，缺失意味着 `MODULE_SIG_FORCE=y` 或 `CONFIG_MODULE_SIG=n`，二者对
   未签名 .ko 的命运截然相反，仅凭此日志无法定罪。
3. **ko 文件不在位（部分可疑）**。diag 报 `ko found: none`，但 late-load 无参
   形式的帮助文本称「ksud picks the embedded KMI」——ksud 是否内置 ko、是否真
   发起了 insmod，日志无法证明；若发起了，dmesg 里的内核报错（EPERM/签名拒绝）
   就是直接证据，而旧诊断窗恰好没截到。

时序侧：stage 5 全程 ~21s（脚本 ~6s + native 15×1s 轮询 15s），在「载不动」的
内核上属纯浪费。

## 3. 根因分析

| 编号 | 根因 | 机理 | 波及 |
| --- | --- | --- | --- |
| RC-5 | `ask_child()` 把任何 `kill(pid,0)` 失败当死亡 | 内核 `kill_ok_by_cred()` 要求调用者四个 uid 字段**全部**等于目标对应字段，或持 CAP_KILL，才放行信号。子进程 cred 被逐对清零的过程中，任何一对清零即打破全等 → EPERM；八字段全零后 EPERM 必然出现。EPERM 在此处恰是「子进程已是 root」的**正面证据**；只有 ESRCH 表示进程不存在 | 36.log：到手的 root 被丢弃，12 次耗尽 → zombie 驻留 |
| RC-6 | 清除循环盲发 + 上限过紧 | 每次尝试对四组字段全部补发 UAF 周期，不查当前值；已清零字段的重发既慢（3.5~8s/周期）又引入 page_miss 风险；上限 12 在单字段滞留时不足 | 38.log：euid 拖死整轮 |
| RC-7 | 交接门禁只看四个值，且子进程 fork 时机过早 | 管道答案只含 uid/euid/gid/egid；suid/sgid/fsuid/fsgid 只能从 `/proc` 读。rootd 的 cred 是 fork 时刻的 `prepare_creds()` 副本，子进程 `uid==0&&euid==0` 即 fork → 半清副本被永久固化 | 39.log：socket 属主 2000，rootd 文件操作按 fsuid=2000 受限 |
| RC-8 | KSU 阶段无「能不能载模块」预检 | CapEff=0（写零范围不含 cap 位）→ `init_module` EPERM 必然；sig_enforce 节点缺失与 `MODULE_SIG_FORCE=y` 特征一致；诊断窗太窄看不到内核报错 | 39/40 两轮：每次白烧 ~21s，拿不到原因 |

**缺陷 → 补丁映射：**

| 缺陷 | 补丁 | 处理 |
| --- | --- | --- |
| RC-5 | C8（0008） | EPERM 分支放行管道验证；ESRCH 才判死亡；cred 子进程消失时并入 rc=5 快速退场 |
| RC-6 | C9（0009） | 逐尝试读 `/proc` 当前值，已清零字段对跳过补发；上限 12 → 24 |
| RC-7 | C9（0009） | 管道答案扩为四值 + `/proc` 八字段门禁（fail-open）；子进程 fork rootd 改为八字段全零条件 |
| RC-8 | C10（0010） | 脚本预检 CapEff/CapPrm 位 16 与 `CONFIG_MODULE_SIG_FORCE`，判死跳过 late-load；宽幅诊断块；native 轮询早退 |

## 4. 方案总览

四条设计原则：

1. **不丢弃到手的胜利**——验证失败时先问「是证据缺失还是真的失败」，EPERM 这类
   正面信号必须放行；procfs 读不到时 fail-open，不再新增「误杀成功」路径。
2. **root 的定义对齐内核**——uid 0 不等于完整 root；交接门禁必须覆盖八个身份
   字段，否则半清 cred 会被 `prepare_creds()` 永久固化进 rootd。
3. **失败要给出可执行的线索**——判死可以，但必须说出原因（cap 缺失 / 签名强制 /
   ko 缺位），并把证据（宽幅 dmesg）留在日志里。
4. **点状修复**——不改变写零原语、不触碰 GhostLock 门禁函数、不改退出码语义；
   capability 写全 1（需要非零载荷）明确划为后续独立立项。

## 5. 逐补丁详解

### 5.1 C8（0008）：kill 探测门禁三分支化

`ask_child()` 原门禁一行判死：

```c
if (kill(g_cred_child_pid, 0) != 0) {
        dprintf(STDOUT_FILENO, "[cred] child %d is dead errno=%d\n", ...);
        log_proc_uid(g_cred_child_pid);
        return -1;
}
```

改为三分支（EPERM 放行、ESRCH 判死、其余按意外处理）：

```c
if (kill(g_cred_child_pid, 0) != 0) {
        if (errno == EPERM) {
                dprintf(STDOUT_FILENO,
                        "[cred] child %d refuses our signals (EPERM): its cred is root now\n",
                        g_cred_child_pid);
                log_proc_uid(g_cred_child_pid);
        } else {
                dprintf(STDOUT_FILENO, "[cred] child %d probe errno=%d (%s)\n",
                        g_cred_child_pid, errno,
                        errno == ESRCH ? "gone" : "unexpected");
                log_proc_uid(g_cred_child_pid);
                return -1;
        }
}
```

EPERM 放行后沿用既有流程：排空应答管道 → 写 go → poll 2s → 读答案。子进程健康
时答案在毫秒级返回（38/40 日志实证），36.log 的场景由此直接翻盘。

`!rooted` 出口新增 `child_gone` 判定，与 C3 的「无 cred」共用 rc=5 快速退场：

```c
int child_gone = kill(g_cred_child_pid, 0) != 0 && errno == ESRCH;
if (daemon_exit && (!g_cred_kva || child_gone)) {
        dprintf(STDOUT_FILENO,
                !g_cred_kva ?
                "[uaf] inject failed: no cred object was planted; exiting cleanly\n" :
                "[uaf] inject failed: cred child died before the handoff; exiting cleanly\n");
        ...  /* 与 C3 相同的清理序列 */
        return 5;
}
```

`FailureDiagnoser.kt` 为新文案新增归因规则（cred 子进程是唯一持页者，其死亡后
驻留纯属泄漏）。

### 5.2 C9（0009）：八字段交接门禁 + 按需补发

新增 `read_proc_ids()`：解析 `/proc/<pid>/status` 的 `Uid:`/`Gid:` 行（各四值，
顺序 real/effective/saved-set/fs），与清除循环的 +4/+12/+20/+28 四组字段一一
对应。这两行位于 `ptrace_may_access` 过滤之外，uid 2000 对 root 子进程可读
（36.log 中父进程三次读出 root 子进程的 `Uid: 0 0 0 0` 已实证）。

cred 子进程的 rootd fork 判据从 `uid==0 && euid==0` 收紧为
`child_ids_all_zero()`（八字段全零；procfs 读失败时退回旧判据，不让通道卡死）：

```c
if (uid == 0 && euid == 0 && child_ids_all_zero(uid, euid) &&
    !g_rootd_forked) {
```

`ask_child()` 签名扩为四值（子进程应答串本就含 gid/egid，仅补解析；旧两值格式
作兼容分支）。验证门禁变为：

```c
if (ask_child(&uid, &euid, &gid, &egid) == 0 &&
    uid == 0 && euid == 0 && gid == 0 && egid == 0 &&
    (!have || ids_zero)) {          /* /proc 读不到时 fail-open */
        rooted = 1;
} else if (uid == 0 && euid == 0 && gid == 0 && egid == 0) {
        dprintf(STDOUT_FILENO,
                "[cred] uid/euid/gid/egid clear, remaining id fields pending\n");
        log_proc_uid(g_cred_child_pid);
}
```

清除循环逐尝试先读 `/proc` 当前值：已清零的字段对打印 `already zero, skip` 并
跳过补发（每跳过一组省一个 3.5~8 秒的 UAF 周期与 page_miss 风险）；读不到
proc 时保持旧行为（四组全发）。上限 12 → 24，日志行同步变为 `/24`。

### 5.3 C10（0010）：KSU 接管预检与诊断

接管脚本在 late-load 之前插入只读预检（脚本以 rootd 身份运行，`/proc/self/status`
即 rootd 凭据的真实快照）：

```sh
CAP_EFF=$(sed -n 's/^CapEff:[[:space:]]*//p' /proc/self/status 2>/dev/null)
CAP_PRM=$(sed -n 's/^CapPrm:[[:space:]]*//p' /proc/self/status 2>/dev/null)
echo "[ksu] rootd CapEff=${CAP_EFF:-unknown} CapPrm=${CAP_PRM:-unknown}" >> "$LOG"
CAN_MOD=1
if [ -n "$CAP_EFF" ]; then
  E=$(( 0x$CAP_EFF & 0x10000 ))
  P=$(( 0x${CAP_PRM:-0} & 0x10000 ))
  [ "$E" -eq 0 ] && [ "$P" -eq 0 ] && CAN_MOD=0
fi
SIG_FORCE=no
if [ -r /proc/config.gz ] && zcat /proc/config.gz 2>/dev/null | grep -q '^CONFIG_MODULE_SIG_FORCE=y'; then
  SIG_FORCE=yes
fi
echo "[ksu] pre-check can_mod=$CAN_MOD sig_force=$SIG_FORCE" >> "$LOG"
```

判死时跳过两次注定失败的 late-load 并写明原因；否则按原有两次尝试执行（原有
live() 探测、daemon 守卫、sync 节奏全部保留）。新增诊断块：uname、ksud
--version、sig_enforce 节点值、ko 状态、**120 行宽幅 dmesg 尾窗**（旧窗只有末
半秒，恰好错过 late-load 报错）。native 侧轮询读到 `[ksu] skip late-load`
标记即提前收场：

```c
if (i >= 2 && log_contains(log, "[ksu] skip late-load")) {
        fprintf(stdout,
                "[ksu] pre-check verdict: module loading unavailable on this kernel (see %s)\n",
                log);
        ksu_sync();
        break;
}
```

整段 stage 5 在「载不动」的内核上从 ~21s 缩到 ~8s，且留下可执行的原因行。
沙箱端到端验证：CapEff 全零环境正确输出 `can_mod=0` 并跳过；位运算分支在
sh/bash/dash 三壳行为一致（Android 的 mksh 同样支持 `0x` 字面量与 `&`）。

### 5.4 C11（0011）：双语设计说明入库

## 7. 安全性论证

1. **EPERM 放行不引入误判**：判定仍由子进程自报（getuid/geteuid/getgid/getegid
   系统调用）与 `/proc` 八字段共同作出；EPERM 分支只是放行既有验证，不改变任何
   判据。半清 cred（如 39.log 的 `0 0 2000 2000`）在 C9 门禁下不会被判 rooted。
2. **ESRCH 退场安全**：cred 子进程是唯一持页者，其消失意味着 UAF 对象引用已全部
   释放；SIGKILL 打在已消失 pid 上无害（返回 ESRCH），waitpid 收尸，随后与 C3
   完全相同的清理序列（关管道/流、`free_aio_hold`、rc=5）。它替代的是一段纯泄漏
   的 `for(;;) pause()`。
3. **procfs 读取权限**：`/proc/<pid>/status` 的 Uid/Gid/State/CapEff 行位于
   `ptrace_may_access` 过滤之外，任何可遍历 /proc 的调用者可读；36.log 已实证
   uid 2000 父进程读取 root 子进程成功。读取失败一律 fail-open，不新增丢弃胜利
   的路径。
4. **子进程 fork 门禁只推迟时机**：rootd 的构造方式不变（仍是 `prepare_creds()`
   副本 + 既有 rootd 流程），唯一变化是 fork 发生在八字段全零之后，副本质量更优。
5. **KSU 预检纯只读**：`sed` 读 status、`zcat` 读 config.gz、`dmesg` 读日志，
   不写任何内核状态；跳过的只是注定 EPERM 的 `insmod`。GhostLock 的 8 个反汇编
   门禁函数未触及，注入引擎写零原语未改变。

## 附录 B FAQ

**Q1：为什么 EPERM 是「已是 root」的证据而不是异常？**
内核 `kill_ok_by_cred()` 要求调用者的 uid/euid/suid/fsuid 四个字段与目标**全部
相等**（或持 CAP_KILL）才放行。写零循环逐对清零后，目标与 uid 2000 的父进程不再
全等，EPERM 必然出现——它出现的时刻恰好是「某一对已清零」的时刻；八字段全零后
更是无一匹配。反过来，进程真正消失时 errno 是 ESRCH(3)。36.log 的 `is dead
errno=1` 后一行还能读到 `/proc/status`，自证误判。

**Q2：39.log 成功了，为什么还要改 W3？**
成功属侥幸链路：rootd 带着半清 cred 副本运行，socket 属主 2000（fsuid 泄漏的直接
证据）。`su -c id` 只读自身状态所以看不出问题，任何需要 fsuid=0 的文件操作都会
受限。40.log 恰好八字段全清后才交接，socket 属主 0——两轮对照证明差异来自交接
时机，C9 把它变成确定性约束。

**Q3：为什么上限改成 24 而不是无限重试？**
skip 机制下， attempts 只在真正有字段滞留时消耗；24 给足当次 boot 页布局的运气
冗余（实测最差 12 次未清一对），同时保留「持续滞留 → 快速退场」的出口。无限重试
会把坏局拖成永久驻留，与 C3 的设计初衷相悖。

**Q4：预检会不会把「其实能载」的内核误判死？**
cap 分支要求 CapEff **与** CapPrm 的位 16 同时为零才判死——只要 Permitted 里有
位，理论上可经 capset 提升-effective（脚本不做、只报告）；sig 分支仅在
`/proc/config.gz` 白纸黑字 `CONFIG_MODULE_SIG_FORCE=y` 时判死。两者都不满足时
late-load 照旧执行，行为与 2.0.36 完全一致。

**Q5：我手改过的构建怎么办？**
建议废弃手改、从干净 main 重建。0008~0010 覆盖手改的全部语义并额外补了
八字段门禁、proc 兜底与宽幅 dmesg；两套实现并存会在后续维护中分叉。

**Q6：这台设备还能装 KernelSU 吗？**
模块装载层面：cap 缺失是确定性障碍，签名强制高度可疑（判别实验见 §8.3）。
不走 LKM 的路（boot 镜像 patch）需要解锁 Bootloader，与本 app 无关。当前设计的
终态是「临时 rootd 通道 + 明确的原因行」，2.0.37 之前每次要白烧 ~21s 且拿不到原因。
